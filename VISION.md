# Vision

But Why exists so that people responsible for software work with coding agents can direct those agents through real software complexity without surrendering judgment over what becomes accepted code.
It serves people who shape software outcomes and delivery, and it helps them guide complexity, divide work, remove repetitive work, and keep human attention on the decisions and deliverables that need discussion.
It owns exactly one thing: the path from a human-approved outcome to accepted code.

## Human intent remains in charge

But Why accepts work only when a human has made the outcome and the authority to advance it clear.
Human authority covers both the required outcome and the consequential design choices that shape the system that delivers it.
Agents can investigate, propose, and implement, but they do not become the source of durable product authority.
Required implementation constraints and design choices that materially affect the system must be made explicit, discussed, or independently judged at the level where they matter.
Only choices with no material effect on the system, its supported behavior, or the evidence needed to judge it remain local to implementation.
Material decisions, uncertainty, and evidence remain visible enough for people to understand why work advanced or stopped.
A later rule or preference does not retroactively erase a judgment that was valid for the code and authority it used.

## Tasks turn outcomes into trustworthy progress

But Why accepts a Task when it names one coherent, observable, independently assessable part of an approved outcome.
A Task makes both the result and its consequential design boundaries clear enough to guide implementation and independent judgment.
Task authoring preserves the complete approved outcome while dividing work into independently understandable, implementable, assessable, and verifiable units.
It accepts splitting work when separate parts need materially independent implementation, failure handling, verification reasoning, or design decisions.
It keeps work together when a split would leave an unsafe, unsupported, duplicated, or unjudgeable result.
It rejects decomposition that merely distributes files, technical layers, or agent effort without creating independently trustworthy progress.
But Why accepts a Plan only when it makes a bounded larger outcome, its consequential decisions, and its proposed Task relationships easier to discuss and judge.
A Plan does not silently claim complete scope or turn a proposed mechanism into approved work.
But Why is not a generic project tracker.

## Acceptance is independent and proportionate

No code change becomes accepted on the assertion of the agent that implemented it.
But Why requires a judgment that is independent from implementation and bound to the code and consequential decisions being judged.
Evidence is valuable when it can distinguish a meaningful failure from a correct result at a justified creation and maintenance cost.
More tests, broader checks, and more durable records are not valuable merely because there are more of them.
When evidence cannot support a trustworthy judgment, But Why makes the gap visible instead of inventing a requirement or a verification mechanism.
Human consent remains required until a class of low-risk work has shown repeated reliable implementation and judgment.
Novel or high-risk work keeps explicit human consent.
Work that executes agent-authored code protects the operator environment from that code.
Nonblocking recommendations are useful only when an accountable triage path can retain, judge, and promote them without confusing them with acceptance.

## Growth preserves the reason to trust the result

But Why accepts delivery through another code-review host when real users need it and the host preserves authority, code identity, and evidence.
It accepts cross-repository outcomes when the outcome, each contributing code change, their judgments, their completion facts, and their recovery boundaries remain clear.
It does not commit that support to a Plan, a state model, a storage model, or a coordination model before evidence establishes the right one.
Storage, coordination, and delivery hosts are replaceable means rather than the product's purpose.
But Why accepts a change to those means only when it keeps the path from approved outcome to accepted code understandable and recoverable.
But Why is not a generic pipeline engine, generic agent runtime, generic repository host, or supply-chain attestation product.
Human-facing descriptions and review guidance make the primary evidence legible before an additional presentation is added.

A change aligns when it helps people responsible for the work shape consequential complexity into independently judged progress without weakening human authority or the meaning of accepted evidence.
A change should be resisted when it hides a consequential decision, makes authority or the code under judgment less clear, or adds machinery that cannot improve a trustworthy decision.
